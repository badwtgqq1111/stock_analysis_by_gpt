## 0. 结论先行

1. **参照对象定位不同**：
   - `QuantaAlpha`（工作区 `/Users/ccs/code/quant/QuantaAlpha`）= **LLM 驱动的自进化因子挖掘框架**
     （`pipeline/evolution/{controller,mutation,crossover,trajectory}` + `pipeline/{factor_mining,loop}.py`，
     论文 arXiv:2602.07085）。它的循环是"假设 → 因子代码 → 回测评估 → 反馈进化"。
   - `Vibe-Trading`（HKUDS）= **个人交易 agent 平台**（FastAPI + React + agent 目录），
     偏"用自然语言驱动交易研究工作流"，不是专门的因子挖掘内核。
   → **因子挖掘该学 QuantaAlpha 的循环范式，不该照搬 Vibe-Trading。**
2. **但 QuantaAlpha 不能直接跑**：它依赖 **Qlib 数据**（`QLIB_DATA_DIR` 需含
   `calendars/ features/ instruments/`），而本机工作区里**没有 Qlib 数据**（已实测：无 `calendars`/`instruments`
   目录、无 `*.day.bin`）；它的 LLM 走 OpenAI 兼容端点（`OPENAI_API_KEY`/`OPENAI_BASE_URL`/`CHAT_MODEL`）。
3. **选定路径（已落地）**：借 QuantaAlpha 的**循环范式**，跑在**我们自己的长面板**上，
   评估端复用本仓库 `scripts/factor_ic_protocol.py` 的口径（月频秩 IC / ICIR / Newey-West t / BH-FDR）。
   实现见 `scripts/llm_factor_mining.py`，LLM 用 **deepseek-flash**。
4. **首轮结果**：2 轮 × 6 个候选 = **12 个 LLM 因子，11 个通过 BH-FDR(q=0.05)**；
   最佳 `sg_value_notoverheat`（成长 + 低估值 + 不过热）**IC 0.1167 / ICIR 0.826 / NW t 6.05**。
   第 2 轮起 LLM 自发把"加法规"改成"乘法规"（交互项），说明回灌 top-3 的反馈是有效的。

## 1. 为什么这么选（而不是先补 Qlib 数据）

| 维度 | 走 QuantaAlpha 原版（先补 Qlib 数据） | **借循环范式 + 跑我们自己的面板（已选）** |
|---|---|---|
| 前置工作 | 把 clean 面板导出成 Qlib `.bin`（约 5,352 只 × 多字段 + calendars/instruments），工作量大、IO 重 | 零前置：长面板已在 `assets/data/meta/cn_sleeve_features_long.parquet` |
| 评估口径 | QuantaAlpha 自己的回测（与我们的准入协议不同） | **直接用本仓库 `factor_ic_protocol.py`**：BH-FDR + Harvey-Liu-Zhu t≥3 + 稳定性 + 冗余聚类 |
| 与我们资产的关系 | 结果需要二次搬运才能进 `[strategies.*]` / clean panel | 因子表达式直接引用面板字段，评估后可入 family 特征集 |
| 可控性 | 需要装 qlib/conda 环境 | 单个脚本 + DeepSeek API |

> 保留选项：若后续要跑 QuantaAlpha 的**完整自进化 + 论文 benchmark**，再补 Qlib 数据导出（工单见 §5）。

## 2. 循环设计（`scripts/llm_factor_mining.py`）

```
字段菜单(25 列) + 方向 + 上一轮 top-3 指标
        │  ── LLM(deepseek-flash) ──►  N 个因子表达式(JSON)
        ▼
安全求值(白名单函数/禁 dunder/禁未来信息)
        │
        ▼
评估：月频秩 IC → ic_mean / ic_std / ICIR / NW t(lag=1) / 正号月占比 / 覆盖率
        │        + 与现有字段的最大 |秩相关|（冗余）
        ▼
落盘 round_<n>/{proposals.json,metrics.csv} → 汇总 factors_all.csv / factors_best.csv
        │
        └──► 回灌 top-3 给下一轮（变异/交叉）
```

**DeepSeek 两个实测坑（已写入脚本注释）**：

1. `deepseek-flash` / `deepseek-reasoner` 是**推理模型**：先输出 `reasoning_content`，
   且 reasoning 计入 completion tokens —— `max_tokens` 给小了只会拿到**空 content**（`finish_reason=length`）。
   脚本用 16,000；`deepseek-chat`（非推理）可小一点。
2. 该端点**不支持** `response_format={"type":"json_object"}`（返回 HTTP 400）→
   改为自由文本 + 代码围栏剥离 + 取首个 `{` 到末个 `}`，并带 3 次重试。

## 6. 交互层：Web 对话面板（2026-10-07 落地）

**结论：值得做对话框交互，但不另起应用** —— 复用本仓库已有的 FastAPI 后端 + Vue 前端，
把"挖掘会话"做成一等公民的资源（`sessions`），而不是把 CLI 塞进 shell。

### 6.1 为什么是对话式，而不是又一个表单

| 维度 | 表单式（一次性提交参数 → 等结果） | **对话式（本方案）** |
|---|---|---|
| 迭代节奏 | 每次改方向都要重跑整轮，看不到中间产物 | 流式回显每轮候选的 IC/ICIR/NW t，**看到哪一条歪了可以立刻换方向再来一轮** |
| 反馈回灌 | 只存在于脚本内部 | 面板把 top-3 与冗余 ρ 直接摆在眼前，人工也能参与"该往哪变"的决策 |
| 可复现 | 参数存在人脑里 | 每次会话落 `output/research/llm_factor_mining_<ts>/`，面板展示 `out_dir`，CLI 可复跑 |
| 成本控制 | 盲目真跑 | 面板内置**自检模式**（`dry_run`，不调 LLM、秒级），先验评估链路再花钱 |

### 6.2 落地形态（三条入口，同一内核）

1. **Vue 应用内页面**：`frontend/src/pages/FactorMining.vue`，路由 `#/factor-mining`，App 导航「因子挖掘对话」。
2. **自包含单页（不依赖构建产物）**：`GET /api/factor-mining/page`，用于"前端构建挂了/只想在本机快速看一眼"。
3. **CLI**：`scripts/llm_factor_mining.py`，仍然是**唯一事实来源**；面板与 API 都只是它的调用者。

### 6.3 接口契约（`backend/api/factor_mining.py`）

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/factor-mining/sessions` | 起会话：`{direction, rounds, proposals, model, dry_run}` → `{session_id, status}`；立刻返回，挖掘在子线程跑 |
| `GET` | `/api/factor-mining/sessions` | 会话列表（状态 / 消息数 / 因子数 / 产物目录） |
| `GET` | `/api/factor-mining/sessions/{id}` | 会话详情：`messages[]`（流式日志）+ `factors[]`（本轮入档因子指标） |
| `GET` | `/api/factor-mining/page` | 自包含对话页 |

**工程约束（已写入代码注释）**：

- 面板加载约占 2GB 内存 → 全局 `threading.Lock` **串行**执行，避免并发把机器打爆；
- 消息分级：`[llm-factor]   OK/ERR …` 归为 assistant，其余归 system，前端按角色渲染气泡；
- 会话结束自动读该轮 `factors_best.csv`（缺失则回退 `factors_all.csv`），把 `name/ic_mean/icir/nw_t/pos_ratio/max_corr_with_fields/fdr_pass/expression` 附到结果区。
- **会话落盘持久化**（2026-10-07 第二轮）：每行日志都原子写 `output/factor_mining_sessions/<id>.json`
  （先写 `.tmp` 再 rename），uvicorn 重启后 `/sessions` 与 `/sessions/{id}` 从磁盘恢复；
  重启时仍标 `running` 的会话自动改判 **`interrupted`**（不假报卡住）；两个页面都有「历史会话」表可一键载入复看。
  会话状态带 `created_at / updated_at`。列表暂无分页与过期清理（遗留）。

| 结论 | 证据 |
|---|---|
| 时间稳定性**不是**问题 | 20/20 因子 5 折 IC 同号率 100%，最差折的 IC 仍为正（最小 0.0015） |
| 滚动前向选择衰减**很小** | 但见下条限定：4 折里 3 次挑中 `GrowthValuePullback`，测试折 IC 0.097/0.104/0.099 vs 全样本 0.104 |
| PBO = **0.000**（CSCV 10 块 / 252 组） | ⚠️ 候选彼此高度相关（都是 value/lowvol/size 近亲），CSCV 只回答"**族内**最优稳不稳"，不回答"这个族本身是不是噪声" → 该数字偏乐观，别当护身符 |
| DSR 分档明显 | `small_val_growth_reversal` 0.99999、`sg_value_notoverheat` 0.99998（小市值×成长×反转）、`GrowthValuePullback` 0.923、低估值×低波一档 0.06~0.93 |
| **瓶颈在增量信息（L2）** | 残差 IC：仅 9/20 > 0，**最大 0.0116**，全部低于 0.02 门槛；FM t：只有 2 个 >2（3.83 / 4.26），**4 个 ≤ −2.2**（系数为负 ⇒ 原始 IC 其实来自被控制的现有列） |
| 参照尺（现有 25 列 IC 加权合成，权重只用前 70% 月份） | 月 IC **0.1049**、NW t 7.22、多空年化 SR **1.24**、DSR 0.865 |
| LLM 因子 vs 参照尺 | 最好的 LLM 因子 IC 0.1044 ≈ 合成（0.1049），多空 SR 1.35 略高，但**残差 IC 仅 0.0014** ⇒ 差异主要是噪声，不是新信息 |

**判断**：这批 LLM 因子**不是新信息**，而是现有 25 列的非线性重组（"低估值×低波×反转×小市值"的各种排列）。
表达式复杂度换不来增量——增量信息的天花板由**数据**决定，不是由公式决定。

**由此改优先级**：

1. **L3 才是判据**：把 `small_val_growth_reversal` / `sg_value_notoverheat` 放进对应 sleeve，
   看 pooled OOS IC 与回撤是否真的改善（现在只有"因子级"证据，没有"组合级"证据）；
2. **给 LLM 新数据源**（资金流/公告事件/另类数据），否则只会继续在 25 列里打转；
3. **L6 试验台账**：DSR 现在用单 run 候选数当 N，偏乐观；应累计历史全部提议次数后重算。

   **不够支撑一次有统计意义的挖掘**。要用分时做因子，绕不开"回补历史"这条路（§12 遗留 1）。

## 15. 日频逐日盯市：口径本身改变结论（2026-10-07 第十二轮）

承 A11/B9（月频 `fwd20` 看不见退市末段），给 L3 加了 `--mark-daily`：持仓仍是月末选出的 5 只，

调仓日扣同样的 21bp 单边成本。日收益矩阵 = clean qfq 日线 ∪ 退市表（2,123 天 × 5,549 只）。

| 臂 | 月频 `fwd20`（样本外 81 月） | **日频逐日盯市** |
|---|---|---|
| `base_v1` | 42.7% / Sharpe 1.33 / 回撤 −23.5% | **22.9% / 0.87 / −37.6%** |

| `random5` | 17.0% / 0.79 / −22.4% | 14.4% / 0.60 / −38.8% |
| `domain_ew` | 17.6% / 0.86 / −24.8% | 13.8% / 0.66 / −36.8% |

**三条结论（第 2 条推翻了我自己前面的判断）**：

2. ⚠️ **"LLM sleeve 跑输现有特征 20pp"（A3）在日频口径下基本消失**：22.9% vs 22.1%、
   Sharpe 0.87 vs 0.86 —— 两者几乎是平手，而 `combo_50_50`（两腿各半）反而最高（25.3% / 0.95）；
   ⇒ 之前那个巨大差距**很大程度是月度测量框架的产物**，不是策略本身的差距；
3. 日频口径下所有手臂的回撤都更深（−36%~−41%），`llm_new` 仍是回撤最大的那个（−41.1%）。

**必须一起看的假设**：逐日盯市用日收盘、无日内执行；停牌/退市后按 0 收益持有；
成本只在调仓日扣一次。若要更严谨，应引入"停牌不可交易 + 退市按最后价清算"的显式规则。

**过程中的两个自纠**：
1. 第一版日频盯市把窗口取成"月份第一天 → 下月第一天"，而持仓来自**月末快照** → 等于把持仓挪前一个月，

2. 因此**第一版那批数字（base_v1 −79.6%/Sharpe −5.78）全部作废**，只保留修正后的结果。

## 22. ST 的 PIT 化：数据工单关闭，但结论是**两个负结果**（2026-10-08 第十九轮）

> 本节回答 §21 第 1 条遗留（结论台账 B13 的后半句）：「ST 过滤是当前名称（非 PIT）
> → 该名单只适合今天选票，不能当历史结论用」。**结论：口径确实错了，但改成正确口径后收益变差。**

### 22.1 数据：中继不行，官方 Pro 行

§21 说"`namechange` 历史本机无该源"是**错的** —— 源有三个，只有一个能用：

| 源 | 契约 | 实测（2026-10-08） | 结论 |
|---|---|---|---|
| 中继 base 网关 | `GET {base}/namechange` | bulk 与带 `start_date`/`end_date` 过滤**一律 HTTP 400** | ❌ |
| 中继 ProMax 网关 | `GET {promax}/namechange?ts_code=X` | 逐 code 可用，**不支持日期过滤**；上游 token 有日配额（间歇 `HTTP 503` / `频率超限(5次/天)`）；12 线程 + 退避实测 0.4 s/只、成功率 ~88%、6039 只约 40 min | ⚠️ 备源 |
| **官方 Pro**（`TUSHARE_TOKEN`） | `POST api.tushare.pro`，`namechange` 支持 `limit`/`offset` | **3 页 × 5000 = 14,231 行、0.7 秒** | ✅ **主源** |

耗时对比：**中继逐只 40 分钟 vs 官方 bulk 0.7 秒**（差 3,400×）。教训：探测接口可用性时不要只测"能不能通"，
要测 **bulk/分页契约**；§21 的记录来自逐 code 探测，于是错误地得出了"bulk 可用"的推论。

落库（`scripts/backfill_cn_namechange.py`，默认 `--source official`）：

```
assets/data/meta/cn_stock_namechange.parquet     13,890 行 / 5,915 只 / 1990-12-01 起
  ts_code|name|start_date|end_date|ann_date|change_reason|is_st|is_delist_risk|is_risk
assets/data/raw/namechange/market=CN/bulk.parquet   审计层（原始分页拼接去重）
assets/data/meta/cn_stock_namechange.manifest.json  覆盖/来源/契约/口径说明
```

除 **128 个上证指数序列**（`000xxx.SH`，本就无更名）外全部覆盖。

### 22.2 模块：`factor_engine/universe_pit.py`

```
load_namechange()                         读区间表（缺文件→空表，绝不静默当"非 ST"）
risk_asof(nc, codes, as_of, ...)          单日：返回 pit_name / is_st / is_delist / is_risk / covered / stale / reason
risk_for_frame(nc, frame, ...)            批量：frame 每行 (code, date) → 当时名称（merge_asof，供回测域）
```

两个口径选择，都写进输出便于核对：
* `anchor="start"`（默认）用**名称生效日**判定，保守、不使用公告信息；
* `anchor="ann"` 用公告日，更激进（公告即剔除）。
* `covered=False` 表示"无记录或命中记录已过期" → 与"非 ST"**分开**暴露，不混为一谈。

**踩过的一个坑（值得记）**：取"as-of 之前最后一条区间记录"时用了
`groupby().last()` —— 它会**跳过 NaN**，于是 `end_date` 取到"最后一个非空值"而 `name` 取到最后一行，
两者错位。症状：`000001.SZ` 得到 `name=平安银行 + end_date=2012-08-01` → 被误判 `stale`，
覆盖面从 97.2% 掉到 46.7%。改用 `drop_duplicates(keep="last")` 后恢复 97.2%。

### 22.5 机制：为什么"错误的"口径数字更好

每月把域内每只票按「PIT 是否剔」×「当前名称是否剔」分四桶，看 20 日前向收益
（`scripts/st_pit_audit.py`，129 个月末 / 116,762 代码·月）：

| 桶 | 含义 | n | 均值 | 中位 | 胜率 | 占比 |
|---|---|---|---|---|---|---|
| `D_clean` | 两口径都不剔（正常票） | 102,488 | +1.31% | 0.00% | 50.0% | 87.8% |
| `B_only_pit` | **仅 PIT 剔**（当时已 ST/退） | 4,714 | **+3.20%** | +1.12% | **53.4%** | 4.0% |
| `A_only_current` | **仅当前剔**（后来才 ST/退） | 7,040 | +0.93% | **−0.67%** | **47.0%** | 6.0% |
| `C_both` | 两口径都剔 | 2,520 | +1.12% | −2.4% | 47.9% | 2.2% |
| └ `B1` 当时仅 ST | | 7,234 | +2.48% | +0.50% | 51.5% | 6.2% |
| └ `B2` 当时含退市整理期 | | **0** | — | — | — | — |

两条读数：

1. **A19**：`A` 桶（"未来才变 ST 的票"）均值 +0.93%、中位 −0.67%、胜率 47.0%，**显著差于正常票**。
   于是"按当前名称过滤历史"＝用**未来信息**剔掉未来输家 ⇒ base_v1 月频从 42.72%（none）降到
   33.08%（诚实 PIT），却还留着 37.70%（含前视的 current）。**过去所有用基础表当前名称做的历史 ST 过滤
   都必须撤回或重跑。**
2. **反直觉**：`B` 桶（**当时就是 ST**）的 fwd20 反而最好（+3.20%）。这解释了为什么加 PIT ST
   过滤会掉 10pp —— 剔掉的是反弹最强的票。**但这不是可交易的 alpha 结论**：这是未扣成本、未做组合的
   单票统计，A 股 ST 板块的"重组/摘帽博弈"需要单独设计（波动、流动性、涨停买不进都要处理），
   已开成新工单 **L13**。

**顺带复现了 B9**：域内"退市整理期"共 99 个代码·月，其中 **有 `fwd20` 的是 0 个** ——
月频 `fwd20` 口径**结构性看不见退市末段**，这次是直接数出来的。

### 22.6 本轮的边界（引用 A18/A19 必须一起说）

* `B` 桶高均值**不等于**"应该买 ST"；未扣成本、未做组合、未处理涨停买不进。
* 月频口径含 A4 的幸存者偏差（+3.6~3.8pp/年）；日频口径按日收盘结算。
* ST 只按**名称**判定；不含停牌时长、涨跌停、流动性（下单预检那半边仍是 §21 的第 2 条遗留）。
* 单市场单段样本（2016-01~2026-09 月末；日频 2020 起）。

### 22.7 区间表自身的覆盖缺口（A20）——决定 PIT 能信到什么程度

`namechange` 不是完美的。Tushare 对 **100 只**股票（其中 **90 只仍在市**）的更名记录在 **2006 年**
就停更——`G股`（股权分置改革完成）前缀的撤销没有被记成一条独立事件。例：

```
600288.SH  大恒科技  2000-11-29 ~ 2006-02-28  其他
600288.SH  G大恒    2006-03-01 ~ 2006-10-08  其他     ← 之后再无记录
```

在**真实上市观测**上（已排除 v4 面板 12.0% 的"未上市占位行"）：

| 指标 | 值 |
|---|---|
| 代码·月总数 | 418,923（141 个月末） |
| `covered=False` | 17,591 = **4.20%** |
| 其中"当前名称是 ST/退"（**可能漏判**） | 2,376 = **0.567%** |

模块对这个缺口**不静默**：命中记录 `end_date` 早于 as-of 时返回 `covered=False / stale=True`，
既不当作"非 ST"，也不编造名称；`select_latest_via_arm.py` 每次都会打印覆盖率（2026-09-30 = 93.4%）。

**这个缺口的方向很重要**：PIT 过滤是**欠检出**的（漏掉的那部分本该被剔）。而 §22.4 已经证明
"剔得越多、收益越低"⇒ **A18 的负贡献是下界**，把 2006 年断档补齐后只会更负。缺口的补法记在工单 L14。

顺带发现（工单 L15，与 ST 无关但影响"面板行数"类口径）：v4 面板 10,440,699 行里有
**1,255,111 行（12.0%）是"未上市占位行"**（`listed_days<0`、市值全空；例如 `001201.SZ` 东瑞股份
2021-04-28 才上市，面板里却有 2015-01-05 起的行）+ 365,440 行（3.5%）是 128 个**上证指数序列**。
两类都进不了域（`listed_days>=365` 且市值非空双重挡掉），对回测结论无影响。
