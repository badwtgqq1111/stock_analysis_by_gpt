## 0.5 执行台 ↔ 因子挖掘：关联必须"看得见"（2026-10-11 补，用户问"这两个 TAB 有什么关联关系么？"）

**关系本身**：`因子挖掘` 是**发起与复看一次研究**的工作台；`执行台` 是**所有 run 的观察台**。
一次挖掘 = 一次 agent run（`kind=mining`）—— 这条关系不是概念，而是**一条真实的数据链**：

```
因子挖掘（会话）                    执行台（轨迹）                        门槛 / 产物
output/factor_mining_sessions/*.json  →  output/agent_runs/<session_id>-mining/run.json  →  因子库 output/factor_library/factors.json
        ↑ 点「去会话 →」                              ↑ 点「轨迹 →」                    候选登记（策略池）
```

* **会话跑完自动出轨迹**：`scripts/agent_run.py from-session` 把会话翻译成一条轨迹
  （阶段 = 每轮提议 `round_N` + 每个因子求值 `eval_<name>` + `probe/fdr_screen/artifacts`；
   门槛 = `probe / propose / evaluate / fdr_screen / factor_library` 五档）。
  API 在会话终态时自动调用（`backend/api/factor_mining.py:sync_run_trace`），也可 `POST /api/factor-mining/sessions/{id}/trace` 手工回填。
* **双向跳转**：执行台轨迹列表里挖掘轨迹标 `mining` 并带「去会话 →」（`#/agent?tab=mining&session=<id>`）；
  挖掘会话列表每条带「轨迹 →」（`#/agent?tab=console&run=<id>-mining`）。
* **门槛表跟随选中的轨迹**：点到挖掘轨迹时看到的是**挖掘的五档门槛**（不再是每日那七个）——
  这正是用户说的"不符合预期"的根源：两个页面原来各看各的，现在看的是同一条链上的不同环节。
* 这条链已验收：`output/verification/p1_68_mining_workbench_20261011/`（Playwright 双向跳转 + `?run=` 深链 + 门槛切换）。
我们采纳这套骨架，但把它落到**有门槛、有产物、可回滚**的量化研究上 —— 对话流里出现的每一张卡都必须能回溯到产物。

## 0. 元素对照（借什么 / 改成什么 / 不借什么）

| 豆包工作台元素 | 我们的因子挖掘工作台 | 判断 |
|---|---|---|
| 左栏「新工作任务 / 新对话」 | 「**新建挖掘会话**」+ **方向模板**（小市值量价交互 / 打板口径 / 行业口径 / 论文复现）—— 点模板直接把方向填进 composer | 借（模板化方向，降低"不知道怎么写"的门槛） |
| 左栏「定时任务」 | 「**每日自动化**」入口（跳到 `/automation`）：我们的 agent 不常驻，`ic-protocol` + `factor_library` 是每日调度跑的 | 改成调度入口（不借常驻） |
| 左栏「技能·连接器·伙伴」 | 「**研究工具**」清单：因子 IC 协议 / 上线闸门 / 影子组合 / 策略池 / 因子库（每条带入口命令与产物链接） | 借（这些就是我们的"工具行"） |
| 左栏「最近」（会话列表） | 挖掘会话列表（状态点 / 方向 / 因子数 / 时间） | 借（已有） |
| 中栏对话流 | 对话流 = 环境行 → 轮次分隔 → **因子卡**（IC/ICIR/NW t/maxρ + 表达式代码块 + 操作）→ 汇总行 | 借，但**结构化**（原来是等宽文本一坨） |
| 代码块右上「运行」/复制 | 因子卡的「复制表达式」「入池成候选」「看产物目录」 | 借 → 换成量化动作（"运行"是重活，走会话而不是按钮） |
| 「搜索 4 个关键词，参考 21 篇资料」 | 「**本次上下文**」chips：面板版本与行数 / 股票数 / 交易日数 / 字段数 / 准入口径（\|IC\|≥0.02、BH-FDR q=0.05、t≥3）/ 上次最佳因子 | 借（把"LLM 在什么证据上说话"摊开；这是通用助手没有的） |
| 底部常驻输入框 + 能力 chips | **底部常驻 composer**：方向输入 + 参数 chips（轮数 / 候选 / 模型 / 自检）+ 模板 chips + 「开始挖掘」 | 借（输入区不该随页面滚走） |

| 右栏（图里没有） | 「本轮因子」（按 \|ICIR\| 排序 + 入池） | 保留我们的产物栏 |

## 1. 为什么不是"表单页"

原来那一版是"左会话 / 中任务+轨迹 / 右产物"的三栏表单：发起一次挖掘要滚到中栏顶部填 4 个输入框，
跑起来之后整页变成一坨等宽日志。问题不在信息量，而在**顺序**：
研究的自然顺序是"我想问什么 → 我看到了什么 → 我拿它做什么"，所以输入区必须**常驻在视线里**（composer），
产出必须是**可点的卡**（复制表达式 / 入池 / 看产物），而不是一行 `print`。

## 2. 落地要点（工作台重排：**✅ 2026-10-12 已实现**；关联链路：✅ 已实现）

1. `frontend/src/components/FactorMiningPanel.vue` 重排为：**左栏（新建 + 模板 + 会话 + 研究工具）｜ 中栏（上下文 chips + 对话流 + 常驻 composer）｜ 右栏（本轮因子 + 入池）**。
2. 对话流的**结构化解析**（纯前端，不改后端日志格式）：把 `[llm-factor] …` 的日志行分成
   `env`（面板行数/字段数）、`round`（第 N 轮返回 M 个）、`factor`（OK/ERR + 指标 + 表达式）、
   `summary`（过 BH-FDR 的个数与最佳）四类；`OK` 行渲染成因子卡，`ERR` 行渲染成错误卡。
   这样"日志格式不变、展示升级"，与 `scripts/agent_run.py` 只解析日志的原则一致。
3. composer 常驻（中栏 `position: sticky; bottom: 0`）+ 方向模板一键填入 + 参数 chips（轮数/候选/模型/自检）。
4. 上下文 chips 里的**准入口径**来自 `/api/agent/factors`（因子库），与下方因子库表**同一份口径**（不另写死一份）。
5. **状态说明（2026-10-12 更新）**：本节 1~4 **已全部实现**（`frontend/src/components/FactorMiningPanel.vue` 重写，
   631 行）+ 新增后端接口 `GET /api/agent/factors/context`（面板规模 / 准入口径 / 上次最佳因子 / **研究工具清单** / **方向模板**）。
   实测（Playwright）：深链 `?tab=mining` 落在挖掘页；左栏模板 4 个 chip、研究工具 7 条；
   上下文 chips 4 个（面板 p0.2.v1·5224 只·683 字段 / 规模 7,058,975 行·2123 交易日 / 准入口径 |IC|≥0.02·BH-FDR q=0.05·|t|≥3 / 上次最佳 rev_vol ICIR 0.683）；
   对话流把 `[llm-factor] OK/ERR` 行解析成**因子卡 ×2**（每张卡 3 个操作：复制表达式 / 入池成候选 / 复制产物路径）；
   composer **常驻**（滚动轨迹后 y=864 < 视口 900）；点模板填入方向、参数 chips 可改；0 控制台报错。
   **口径同源**：上下文 chips 的准入口径直接取 `/api/agent/factors` 的 `criteria`（有测试锁：两者必须相等）。
6. 明确不做：不让按钮直接"运行表达式"（单表达式复算要重载 2GB 面板，应该走一次 `rounds=1 / proposals=1` 的会话，且要排队）；
   不做语音输入；不做多会话并行（服务端串行）。

7. **（2026-10-12 追加，P2.51）灵感来源 / 知识库**：左栏再加一块「灵感来源 / 知识库」—— 15 个来源（含用户点名的
   QuantPedia / Seeking Alpha / FRED 与聚宽 JoinQuant）按地区分组，点开看**怎么用 / 坑 / 入口**，
   并带「用它的方向」把该来源的方向模板填进 composer；方向模板从 4 条扩到 12 条（每条绑一个来源）。
   注册表在 `config/research_sources.json`（**加一条不用改代码**），接口 `GET /api/agent/research-sources`，
   纪律见 `docs/todo/P2_51_research_sources.md`：**来源只给方向、不给证据**。
